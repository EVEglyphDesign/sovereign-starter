The two files

NARROWING.md

What you want the AI to do or not do. In your voice. The AI reads this first, before it acts for you. Ten worked-example rules to copy, edit, or delete.

View raw

OBSERVATIONS.md

What actually happened. Every time the AI's work put something on your plate that it should not have, you log one row. Individual rows can be sloppy; the aggregate is what matters. The pattern will not lie.

The loop

OBSERVATIONS.md is the evidence. NARROWING.md is the response. When three observations of the same shape stack up, a rule enters NARROWING.md. If the rule closes the shape, it was right. If the shape keeps repeating, the rule was under-specified.

That is the whole loop. Two files you write in your own words, and a habit of adding rows to the register when the AI wastes your time.

Five-minute start

  1. Download or copy both files into whatever surface you already use with your AI.
  2. Read NARROWING.md. Delete rules that do not apply to you. Rewrite the ones that do into your own words.
  3. Read OBSERVATIONS.md. Delete the example row.
  4. Point your AI at the two files: "Read NARROWING.md before you answer, and log any miss to OBSERVATIONS.md" is enough of an instruction.
  5. Start using the AI normally. When it wastes your time, add one row. That is the loop.

Where to keep the two files

The files are plain Markdown. They work anywhere you can keep two plain-text documents your AI can read.

  • ChatGPT project files — upload both files. First message: "Read NARROWING.md first."
  • Claude project knowledge — attach both files. Reference NARROWING.md in the system prompt.
  • A Notion page — one page per file inside a parent page. Copy the parent URL into the AI's context.
  • A Google Doc — one document per file, in a shared folder. Copy the folder URL into the AI's context.
  • A folder on your computer — ~/ai-notes/NARROWING.md and ~/ai-notes/OBSERVATIONS.md.
  • A GitHub repository — this repository is the reference layout, but you do not need a repository to use the method. A repository is useful when you have graduated past what a scratchpad can hold.

When two files stop being enough

Graduate to the canon plug-in

When the operating agreement gets wider than a page — you are running a project that needs a bilateral terms section, inherited compliance (finance, information security, GDPR, sovereignty), a reference framework, and project-specific rules — the two-file method still holds, but NARROWING.md outgrows a single scratchpad file.

The canon plug-in is that same two-file method at project scale. CANON.md replaces NARROWING.md with a layered structure (Terms + boot contract + inherited compliance + blueprint + framework + project rules); OBSERVATIONS.md stays the same shape and adds a Type-Δ row for every change to the canon so the agreement stays bilateral.

Same shape. Same loop. Wider content.

Why two files instead of one

One file collapses two questions into one: what do I want and why do I want it. That works for a week. It stops working the moment you have more than a page of rules, because the rules and the evidence for the rules cannot both be scannable on the same page.

Splitting the two lets NARROWING.md stay short — a first read — while OBSERVATIONS.md grows freely as the evidence accumulates. The AI reads only the short file every session. The long file exists to be read once when a rule feels wrong, or when a new one is added.

Why letters for classes and not names

Letters are cheap to add. A letter never has to be renamed because it was a poor description; a name does. The register in OBSERVATIONS.md starts with ten classes (C, R, D, L, E, S, I, P, T, H) — add your own when a new shape appears. The letters do not have to match anyone else's letters. They only have to be stable for your register.
